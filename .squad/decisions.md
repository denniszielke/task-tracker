### 2026-10-16T10-16-20: Late notifications Q3: explicit bounded demo workload, production percentiles remain blocked

**What:** Late notifications Q3: explicit bounded demo workload, production percentiles remain blocked
**Why:** 2026-10-16 — Open question 3. Demo admission limits: 100 orders, 200 repair jobs, 500 directed edges, maximum dependency depth 32, 20 shops, and 100 queued out-of-order events per lifecycle. ### 2026-10-16T10-16-20: Late notifications Q4: five-minute missing-edge buffer and explicit absolute-time propagation
**By:** Lead
**What:** Late notifications Q4: five-minute missing-edge buffer and explicit absolute-time propagation
**Why:** 2026-10-16 — Open question 4. Each dependency has optional bufferMinutes; absent/null defaults to 5 minutes, explicit 0 means no buffer, negative/nonfinite values reject. Incoming arrival/completion plus this buffer must be <= requiredReadyAt to be achievable (equality is not affected). Demo fixture uses explicit 0-minute edges where reproducing PRD reference timings. Job projected start=max(plannedStartAt, all prerequisite readiness+buffer); projected completion=max(estimatedCompletionAt if provided, projected start+durationMinutes); do not sum delays across converging paths. Propagate through the DAG even when a direct edge is still achievable, since slack may absorb a delay. Keep original planned/committed times immutable; notification impact is derived, not automatic schedule rebooking. Rationale: conservative explicit default and deterministic buffer/equality/diamond behavior. Production dependency: operations-approved route/preparation buffers, maintained schedules/durations/actual completion data and graph ownership.

### 2026-10-16T10-16-20: Late notifications Q5: bounded retry, in-app escalation and separate rejection state
**By:** Lead
**What:** Late notifications Q5: bounded retry, in-app escalation and separate rejection state
**Why:** 2026-10-16 — Open question 5. Attempt immediately, then after failures at +1s, +5s, +30s, +120s relative to the preceding failed attempt: five attempts total per notification revision, then Failed. No jitter in demo so tests are deterministic. Disconnected is a failed attempt, not delivery; each shop is independent. Operations may retry the latest failed revision manually (reset its attempt budget but retain all attempts). Reconnect expedites latest Pending/Retrying revisions; Failed requires explicit manual retry. Escalate in operations UI/audit: Warning at 5 minutes after notification creation without Accepted acknowledgement; Error at 15 minutes, immediately on delivery exhaustion, or immediately on a Rejected acknowledgement. Recipient is demo operations queue; no external pager. Valid Rejected acknowledgement remains an acknowledgement audit record but DOES NOT mark Acknowledged/success; show rejection and a contact-shop/retry action. Terminal revisions still require delivery and may be acknowledged but do not raise unacknowledged-delay timers after successful terminal delivery. Rationale: actionable explicit outcomes, no silent infinite retries or fake alerts. Production dependency: agreed support owner/on-call contacts, severity thresholds, retry/backoff/jitter policy and real alert routing.

### 2026-10-16T10-16-20: Late notifications Q6: acknowledgements confirm processing, never reschedule jobs
**By:** Lead
**What:** Late notifications Q6: acknowledgements confirm processing, never reschedule jobs
**Why:** 2026-10-16 — Open question 6. Version-1 acknowledgement supports acknowledgementId, notificationId, revision, acknowledgedAt, outcome Accepted|Rejected, optional reasonCode/comment only. Do not support proposed job start times or modify planned/actual schedules through acknowledgement. Reject unsupported schema properties rather than silently rebooking. A new acknowledgementId can acknowledge another revision; once a shop has an outcome for a notification revision, identical semantic repeats are idempotent and different outcomes/reasons/comments conflict. Rationale: PRD explicitly excludes automatic scheduling and acknowledgement must not be confused with a scheduling command. Production dependency: separate scheduling product contract if proposals are later wanted.

### 2026-10-16T10-16-20: Late notifications Q7: bounded local history, explicit persistence failure, no durability claims
**By:** Lead
**What:** Late notifications Q7: bounded local history, explicit persistence failure, no durability claims
**Why:** 2026-10-16 — Open question 7. Store versioned demo state in one namespaced localStorage snapshot `pickup-orders.late-notifications.v1`; injected memory storage for tests. Preserve all events, notifications/revisions, attempts, acknowledgements and operational audit in a workspace until explicit Reset demo. No time-based pruning (and therefore no loss of idempotency tombstones). Bound snapshot to 2,000,000 UTF-8 bytes and audit records to 10,000; when admission/persistence would exceed either limit reject the mutation with STORAGE_FULL and show an operations next action (export inspection through UI if implemented, otherwise reset demo after review). No silent clearing, trimming or fallback from unavailable/corrupt storage to supposedly persisted state. UI may deliberately choose an explicitly labelled volatile memory session if localStorage is unavailable, with persistenceState=volatile and reload-loss warning. Atomic snapshot write succeeds before command success/subscriber notification/business effects are exposed. Corrupt/unknown snapshot versions surface a storage error; preserve value until explicit reset. Rationale: demonstrable reload recovery with bounded resource usage, not durable server retention. Production dependency: legal/product retention periods, encryption/access policies, archival/deletion/idempotency retention, backups, transactional datastore and cross-process locking.

### 2026-10-16T10-16-20: Late notifications Q8: exact terminal values only, preserve canonical Late classifier
**By:** Lead
**What:** Late notifications Q8: exact terminal values only, preserve canonical Late classifier
**Why:** 2026-10-16 — Open question 8. Existing orders retain status labels Awaiting pickup, Driver assigned, In transit; exact Delivered is delivered and exact Cancelled is cancelled in the notification adapter only. Do not guess aliases or alter classifyDelivery: its existing precedence Delivered, missing inspectionAt=>Unknown, inspectionAt<now=>Late, equality=>On track is unchanged, including malformed-data error behavior. Thus a Cancelled order may still classify Late under the existing filter but must not auto-publish a new late lifecycle. New repair-job states are Scheduled, In progress, Completed, Cancelled. Completed requires actualCompletionAt; vehicle.delivered requires actualAt. Terminal dependent jobs are excluded as active impacts; a completed prerequisite uses actual completion readiness, while cancelled prerequisite branches cannot run and send cancellation semantics. Vehicle delivery does NOT blindly resolve late downstream work: recalculate from actual arrival and resolve only shops with no remaining impact. Unknown terminal aliases reject on new job schemas; upstream normalization is deferred pending approved mapping. Rationale: prevent accidental semantic changes or premature resolution. Production dependency: agreed upstream order/job state mappings and reliable actual arrival/completion capture.
